OpenObserve · Metrics Benchmark

One Dataset, Four Systems — Benchmarking Prometheus, Mimir, and OpenObserve on Metrics Ingestion and Queries

We pushed the same ~2.2 billion samples through one OTel Collector into four systems simultaneously, stopped ingestion, and ran the exact same PromQL against each over an identical frozen window.

Then we ran the whole thing twice, changing only the memory limit — 28 GB, then 14 GB — because those turn out to answer different questions.

The contenders are four deployments with fully aligned configurations: Prometheus, Grafana Mimir, OpenObserve (Parquet format), and OpenObserve (Vortex format). Each gets a dedicated EC2 m7gd.2xlarge with its data on the node's local NVMe, query caches disabled, and identical query limits and timeouts — so that neither the disk nor a protective default decides the outcome.

The setup

Pin down the variables first — the numbers only mean something afterward.

  • Hardware: one dedicated EC2 m7gd.2xlarge per system, 7 CPU, 474 GB local NVMe; container memory limit 28 GB in round 1 and 14 GB in round 2
  • Versions: Prometheus quay.io/prometheus/prometheus:v3.6.0; Mimir grafana/mimir:latest; OpenObserve v0.92.0, two OpenObserve deployments as an A/B: one with ZO_FILE_FORMAT=parquet, one with ZO_FILE_FORMAT=vortex. All single-node
  • Fairness settings: all query caches disabled; OpenObserve's Parquet filter pushdown disabled (ZO_FEATURE_PUSHDOWN_FILTER_ENABLED=false — it's on by default, but in our metrics tests it actually slowed queries by ~20%, so we turned it off; the switch only affects Parquet, Vortex's filter pushdown is always on)
  • Ingestion: 2026-08-09 12:47–21:10 CST (8h23m), then stopped — every query runs against a frozen dataset
  • Query range: four windows of 30m / 1h / 3h / 6h, all ending 2026-08-09 20:00 CST, pinned absolutely so successive runs measure the same data
  • Step: computed per window the way Grafana does — max(15s, range / 1000) rounded up to a tidy interval — rather than pinned at 15s. That is 15s for 30m/1h/3h and 30s at 6h, so every window asks for ≤720 points instead of 1,440 at 6h
  • Measurement: from a pod inside the cluster, in the same AZ as all four systems. Every query runs 3 times and the tables report the median, plus one cold first-touch request recorded separately and excluded from it

How the measurement is taken

Four choices here move the numbers more than any configuration above, so they are worth stating outright.

Queries are issued from inside the cluster. The obvious way to drive a benchmark from a laptop is kubectl port-forward, and it invalidates the result. The fastest query in this set answers in about 100ms; forwarding adds far more than that, and it does not add a constant — the same query measured 1,656ms to 2,862ms of pure overhead across repeats. That does not merely inflate the numbers, it destroys the ratios between systems, which is the only thing a comparison is for. Everything here is measured from a pod in the cluster, in the same availability zone as all four systems, on a node that is not under test.

Every system's data is on node-local NVMe. Each system gets a dedicated m7gd.2xlarge and writes to that node's instance store, so storage is not a variable between them and no query is measuring EBS throughput.

Ingestion is stopped before anything is measured. All four query a frozen dataset over absolutely-pinned time windows, so a run repeated an hour later sees the same bytes. Load still arriving during measurement would make each system's numbers depend on what it happened to be compacting.

The step is computed, not pinned. A fixed 15s step makes the point count grow with the window — 1,440 points at 6h — which no dashboard would ever request. Grafana asks for roughly the panel width in pixels, so this benchmark uses its rule: max(15s, range / 1000) rounded up to a tidy interval. That is 15s at 30m/1h/3h and 30s at 6h. It matters because Prometheus and Mimir cost scales with the number of output points, while OpenObserve's scales with the data scanned — on a fixed 3-hour window, widening the step from 36 to 720 points moved Prometheus 1.68s→3.92s and Mimir 1.14s→4.11s, but OpenObserve only 3.45s→4.63s. Publish your step whichever way you go; it is the single biggest lever on absolute latency here.

One more: the first request against each cell is recorded separately and excluded from the medians. A cold first touch pays for file opens, index loads and page-cache misses, and answers a different question — "what does the first query after a gap cost?" — than the warm runs that follow.

How the data was generated

The workload comes from openobserve/fake-webserver:v2: 24 pods, each producing ~45k time series, so the histogram's _bucket metric carries roughly 1.09 million active series.

On the collection side, a separately deployed OTel Collector writes the same data to all systems under test simultaneously — every system receives the exact same samples, ~2.2 billion across the codelab_api_* metrics, spanning 1,085,760 bucket series.

Cardinality of the two key metrics:

  • codelab_api_request_duration_seconds_bucket: 1,085,760 series (high cardinality; used by the histogram queries)
  • codelab_api_request_duration_seconds_count: 41,760 series (used by the irate query)

Remember that bucket cardinality. A million series is where the results start to diverge.

Ingestion: resource usage

Sampled every 10 minutes across the 8h23m ingestion, at the 28 GB memory limit. Disk is the settled figure, 14.8 hours after the last write:

SystemCPU (cores, typical)RSS (steady)Disk (settled)
Prometheus1.3–1.93.2–4.1 GB11 GB
Mimir0.7–1.14.5–5.5 GB18 GB
OpenObserve (Parquet)1.6–2.21.5–2.0 GB28 GB
OpenObserve (Vortex)1.6–2.01.5–2.1 GB27 GB

Three observations:

Memory is OpenObserve's clear win. Sampled every ten minutes across 8h23m of ingestion, Prometheus ran 3.2–4.1GB and Mimir 4.5–5.5GB, both moving in a sawtooth as head blocks fill and compact. Both OpenObserve variants stay flat at 1.5–2.1GB — roughly half of Prometheus and a third of Mimir. Once ingestion stops everything collapses: Prometheus to 2.4GB, Mimir to 2.5GB, and both OpenObserve deployments to under 600MB; the ingestion-time figures are buffers and WAL, not resident working set.

OpenObserve pays for it in CPU. ~1.6–2.2 cores versus Prometheus's ~1.3–1.9 and Mimir's ~0.7–1.1. The extra cycles go into columnar encoding and compression. At identical ingest throughput, that is the price paid for query performance and low memory.

Memory here is RSS — the memory the process actually holds, the number top shows in its RES column — not page cache the kernel is free to reclaim.

Disk usage is largest for OpenObserve, and it deserves context. 28GB versus Prometheus's 11GB and Mimir's 18GB, over 8h23m of ingestion. A general-purpose columnar format keeps full detail rather than applying TSDB-style XOR/delta compression tuned specifically for time series; in exchange, the same data simultaneously serves SQL, PromQL, and arbitrary dimensional analysis, and maps naturally onto object storage, where it typically lives in production at a very different unit cost. Parquet and Vortex tie, at 28 and 27GB. All four figures were taken 14.8 hours after the last write, once every system's compaction and cleanup had finished.

Disk is the one number you cannot measure right after stopping ingestion. Watched live across this run, Mimir's volume went up after the writes stopped — 21.6GB at 21:10, 29.5GB by 22:23 — because the compactor writes the merged block first and keeps the sources for half a day. It fell back to 18GB only once deletion_delay expired. Read at stop+2h, Mimir looks the same size as OpenObserve; settled, OpenObserve uses 1.6× more. Only Mimir moves — Prometheus and OpenObserve read the same at both times. Two stable readings 30 seconds apart prove nothing.

The wait is not symmetric. OpenObserve deletes merged-away files after 2h (ZO_COMPACT_DELETE_FILES_DELAY_HOURS) and settles at ~2h; Prometheus deletes source blocks immediately after compaction and settles at ~2–3h; Mimir needs ~14h, and neither of its timers can usefully be shortened. Its PVC holds two copies: the filesystem bucket, whose superseded source blocks the compactor keeps for deletion_delay: 12h, and the ingester's local TSDB, kept for blocks_storage.tsdb.retention_period: 13h after upload. Lowering the first only moves an intermediate drop earlier — the volume still waits on the 13-hour timer — and the second must not be lowered at all: it is aligned with query_store_after: 12h, and dropping the ingester's copy early makes queries silently return incomplete results. Wait ~14 hours, or say your disk figures are provisional.

Measuring early biases the comparison towards OpenObserve, by inflating the systems it is compared against. Wait ~14 hours after the last write, or label your disk figures provisional.

Against a million-series unfiltered histogram, the defaults decide the outcome before the engines do: Prometheus and Mimir both refuse the query at stock limits. Given the same allowances and the same 600s clock, all four finish every window — and the spread is an order of magnitude.

Every one of these is a protective default doing its job, and this benchmark raises all of them — --query.max-samples=1e9, max_fetched_chunks_per_query=20e6, ZO_METRICS_MAX_SERIES_RESPONSE=40000, ZO_METRICS_MAX_POINTS_PER_SERIES=1e7 — together with a uniform 600s timeout. At 6h OpenObserve then finishes in 47 seconds against Prometheus's 4.5 minutes and Mimir's 4.3 minutes.

Parquet vs Vortex: same engine, two file formats

The only difference between the two OpenObserve deployments is ZO_FILE_FORMAT. The results split cleanly by query type:

irate and unfiltered histogram: a tie. When queries must scan all the data, the two formats trade places within 5–10% — no decisive winner. Disk usage ties as well (28 and 27GB).

Filtered histogram: Vortex is consistently ~3× faster.

The pattern is remarkably stable and widens with the window: 2.9× at 30m, 2.9× at 1h, 3.2× at 3h and 3.2× at 6h. At the 6-hour window Parquet is slower than both Prometheus and Mimir on this query while Vortex is roughly twice as fast as either — for dashboard-style filtered workloads the format choice is worth more than the engine choice.

Put differently: the "filter by service/endpoint" queries that dominate real dashboards are exactly the shape where Vortex gains the most.

Round 2: the same benchmark at 14 GB of memory

28 GB is a comfortable sizing for a million active series. 14 GB is a plausible one. Running the identical benchmark at both — same frozen dataset, same queries, same absolute time windows, only the container limit changed — turns "how fast is it" into a second question: what still runs at all?

Halving the memory changes almost nothing — except that Prometheus stops being able to answer. Every cell landed within 5% of its 28 GB value, with two exceptions: the million-series unfiltered histogram at 3h and at 6h, where Prometheus was OOMKilled both times, mid-query, after 158s and 192s respectively (restartCount=2, exitCode=137).

The reason shows up in a direct measurement. A single 3-hour unfiltered histogram peaks at 18.7GB RSS in Prometheus against 4.25GB in Mimir — Prometheus loads samples into memory, and at --query.max-samples=1e9 and ~16 bytes per sample that is ~16GB, matching the measured rise almost exactly. Raising the limit so the query can run, and having the query consume 20GB, are the same decision. Mimir answers it in a quarter of the memory and takes 35% longer; on a 14 GB box that is the difference between an answer and a restart.

Worth noting how this was captured at all: curl cannot distinguish an OOMKill from a network failure — both surface as HTTP 000. The harness records a per-request timestamp and samples container restart state before and after each run, so finishedAt=16:58:26Z could be matched to the exact request that triggered it. Without that, this result would read "connection failure" and mean nothing.

The bottom line

Put the same ~2.2 billion samples and ~1.09 million bucket series in front of four systems, and the results condense to four sentences:

  • Ingestion memory: OpenObserve stays flat at 1.5–2.1GB — about half of Prometheus and a third of Mimir, and under 600MB once ingestion stops. The trade-off is ~2.5× the disk of Prometheus (typically on object storage)
  • Everyday queries: on irate at 6h, OpenObserve is ~10.8× faster than Prometheus and ~8.7× faster than Mimir; on filtered histograms Vortex leads Prometheus by 1.9×, while Parquet trails it by 1.7×
  • The high-cardinality limit: on the million-series unfiltered histogram, stock limits make Prometheus and Mimir refuse the query outright. Raised to match, all four complete — OpenObserve in 27s at 3h against 3.2 and 4.1 minutes
  • The format race: Vortex is 2.9×–3.2× faster than Parquet on filtered queries and ties on full scans — for dashboard-style filtered workloads, Vortex is the better default
In high-cardinality metrics, the real dividing line isn't a few hundred milliseconds of latency — it's whether your queries still return at all once series counts cross a million.
