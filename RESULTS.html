OpenObserve · Metrics Benchmark

One Dataset, Four Systems — Benchmarking Prometheus, Mimir, and OpenObserve on Metrics Ingestion and Queries

The problem with most metrics-system benchmarks is that everyone tests their own way: different data, different hardware, different queries. The results can't be compared.

So we took the same 7.1 billion samples, pushed them through one OTel Collector into four systems simultaneously, and ran the exact same PromQL against each.

The contenders are four deployments with fully aligned configurations: Prometheus, Grafana Mimir, OpenObserve (Parquet format), and OpenObserve (Vortex format). Each system gets a dedicated EC2 c7g.2xlarge (7 CPU / 14GB RAM / gp3 500GB), all query caches disabled, same time range, every query run three times.

The setup

Pin down the variables first — the numbers only mean something afterward.

  • Hardware: one dedicated EC2 c7g.2xlarge per system, 7 CPU / 14GB RAM available, gp3 500GB disk
  • Versions: Prometheus quay.io/prometheus/prometheus:v3.6.0; Mimir grafana/mimir:latest; OpenObserve 0.92.0-rc3, two OpenObserve deployments as an A/B: one with ZO_FILE_FORMAT=parquet, one with ZO_FILE_FORMAT=vortex. All single-node
  • Fairness settings: all query caches disabled; OpenObserve's Parquet filter pushdown disabled (ZO_FEATURE_PUSHDOWN_FILTER_ENABLED=false — it's on by default, but in our metrics tests it actually slowed queries by ~20%, so we turned it off; the switch only affects Parquet, Vortex's filter pushdown is always on)
  • Query range: 2026-08-06 00:00 – 03:00 (CST), every query executed 3 times, all three results shown in the tables

How the data was generated

The workload comes from openobserve/fake-webserver:v2: 10 nodes, each producing 50k time series by default — 500k series total. A pod restart mid-test changed pod names and doubled the count, so the final active series count is roughly 1 million.

On the collection side, a separately deployed OTel Collector writes the same data to all systems under test simultaneously — every system receives the exact same samples, 7.1 billion in total.

Cardinality of the two key metrics:

  • codelab_api_request_duration_seconds_bucket: 1,085,760 series (high cardinality; used by the histogram queries)
  • codelab_api_request_duration_seconds_count: 41,760 series (used by the irate query)

Keep that million-series bucket cardinality in mind — it's the root cause of Prometheus and Mimir falling over on the unfiltered histogram later.

Ingestion: resource usage

Steady-state resource usage during ingestion:

Prometheus0.62.0 GB19.9 GB

OpenObserve (Parquet)1.00.9 GB95 GB
OpenObserve (Vortex)1.00.9 GB95 GB

Three observations:

Memory is OpenObserve's clear win. With a million active series, Prometheus and Mimir must keep series indexes and head blocks resident in memory — 2.0GB and 2.8GB respectively. Both OpenObserve variants hold steady at 0.9GB, roughly a third of Mimir. As cardinality keeps climbing, TSDB-style memory grows near-linearly with active series, while OpenObserve's columnar write path is far less cardinality-sensitive — a fundamental difference in high-cardinality scenarios.

OpenObserve pays for it in CPU. 1.0 core versus Prometheus's 0.6 and Mimir's 0.4 — the extra cycles go into columnar encoding and compression. At identical ingest throughput, that's the price paid for query performance and low memory.

Disk usage is largest for OpenObserve, and it deserves context. 95GB versus Prometheus's 19.9GB and Mimir's 34GB. A general-purpose columnar format keeps full detail rather than applying TSDB-style XOR/delta compression tuned specifically for time series; in exchange, the same data simultaneously serves SQL, PromQL, and arbitrary dimensional analysis, and maps naturally onto object storage — in production those 95GB typically live on S3, not a local disk, at a very different unit cost. Parquet and Vortex tie on disk usage at 95GB each.

Against a million-series unfiltered histogram, the question is no longer "who's faster" — it's "who finishes at all". Of the four systems, only OpenObserve returned results on every window.

To be fair, both Prometheus's and Mimir's errors are protective limits. Raising the relevant knobs (e.g. Mimir's -querier.max-fetched-chunks-per-query) might let the queries complete — but that means allowing a single query to consume far more memory, at your own risk on a 14GB machine. OpenObserve's columnar execution path doesn't need to load all series chunks into memory, so with default settings it finishes the 1h window in under 5 seconds and the 3h window in 12–14 seconds.

Parquet vs Vortex: same engine, two file formats

The only difference between the two OpenObserve deployments is ZO_FILE_FORMAT. The results split cleanly by query type:

irate and unfiltered histogram: a tie. When queries must scan all the data, the two formats trade places within 5–10% — no decisive winner. Disk usage ties as well (95GB each).

Filtered histogram: Vortex is consistently 2× faster or more.

The pattern is remarkably stable: 2.1× at 30m, 2.2× at 1h, 2.4× at 3h — the longer the window, the bigger Vortex's edge.

Put differently: the "filter by service/endpoint" queries that dominate real dashboards are exactly the shape where Vortex gains the most.

A side observation: cold vs. hot queries and disk type

Beyond the headline numbers, one phenomenon is worth recording.

The cold/hot gap. OpenObserve's histogram queries over the 3-hour window all take around 30 seconds on the first cold run (data not in the OS page cache), versus 2 seconds hot; dropping the page cache with echo 3 > /proc/sys/vm/drop_caches and re-running brings it right back to 30 seconds.

The bottleneck is disk throughput — the arithmetic makes it obvious. The query engine log shows:

promql->search->storage: load files 76,
scan_size 137424238093, compressed_size 3627283262, took: 3 ms

Locating the 76 files via metadata took just 3ms, but the compressed data to read off disk is 3.6GB. The test used gp3 at its default configuration — 3,000 IOPS, 125MB/s throughput: 3.6GB ÷ 125MB/s ≈ 29 seconds, which lines up almost exactly with the measured 30 seconds. Cold query time is spent almost entirely reading data off the disk.

We verified the diagnosis: after switching gp3 to io2, the same cold query takes only about 4 seconds (3.52s measured) — barely distinguishable from a hot run. The cold-query bottleneck is purely storage bandwidth; a faster disk or an added cache layer buys an order-of-magnitude improvement.

The bottom line

Put the same 7.1 billion samples and ~1 million active series in front of four systems, and the results condense to four sentences:

  • Ingestion memory: OpenObserve at 0.9GB — half of Prometheus, a third of Mimir; the trade-off is ~0.4–0.6 more CPU cores and larger disk usage (95GB, typically on object storage)
  • Everyday queries: on irate, OpenObserve is ~8× faster than Prometheus and ~21× faster than Mimir; on filtered histograms, 1.4×–8.8× faster
  • The high-cardinality limit: on the million-series unfiltered histogram, Prometheus errors on every window, Mimir errors at 3h — only OpenObserve returns results on all windows
  • The format race: Vortex is consistently 2×+ faster than Parquet on filtered queries and ties on full scans — for dashboard-style filtered workloads, Vortex is the better default
In high-cardinality metrics, the real dividing line isn't a few hundred milliseconds of latency — it's whether your queries still return at all once series counts cross a million.
