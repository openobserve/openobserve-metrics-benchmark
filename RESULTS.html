OpenObserve · Metrics Benchmark

One Dataset, Four Systems — Benchmarking Prometheus, Mimir, VictoriaMetrics and OpenObserve on Metrics Queries

We wrote the same 2.2 billion samples — 1.34 million series — into four systems at once, then ran the exact same PromQL against each over the same fixed time windows.

Every system had the same 12 CPUs and 24 GB of memory, the same local NVMe disk, and the same query limits. Across 4 queries × 4 time windows — 16 combinations — OpenObserve answered every one fastest.

The contenders: Prometheus, Grafana Mimir, VictoriaMetrics and OpenObserve v1.1.1. Each runs single-node on its own dedicated EC2 m7gd.4xlarge, writes to that node's local NVMe, has result caches disabled and identical query limits and timeouts — so that neither the disk nor a protective default decides the outcome.

The setup

  • Hardware: one dedicated EC2 m7gd.4xlarge per system (16 vCPU, 64 GiB, local NVMe); every container limited to 12 CPU / 24 GB, requests equal to limits — for ingestion, compaction and queries alike
  • Versions: Prometheus v3.6.0; Mimir 3.2.2; VictoriaMetrics v1.154.0, single node; OpenObserve v1.1.1, standalone, Parquet storage with metrics index. All single-node
  • Fairness settings: result caches off (VictoriaMetrics -search.disableCache, OpenObserve ZO_RESULT_CACHE_ENABLED=false; Prometheus and Mimir have none configured); query limits raised to the same level on all four; a 600s timeout everywhere
  • Data: 7 hours of samples at exactly 15-second intervals, 2026-09-28 03:00–10:00 UTC, written once to all four; ingestion finished before any query ran
  • Query range: four windows of 30m / 1h / 3h / 6h, all ending 2026-09-28 10:00 UTC
  • Step: computed per window the way Grafana does — max(15s, range / 1000) rounded up to a tidy interval: 15s for 30m/1h/3h and 30s at 6h, so no window asks for more than 720 points
  • Measurement: from a pod inside the cluster, in the same AZ as all four systems. Each cell is run 5 times, the whole matrix twice back to back, and the tables report the median of both passes

Prometheus launch arguments — the remote write receiver so the load can be pushed in, and the last two raised from their defaults so the million-series histogram runs instead of being refused — plus a 2-hour out-of-order window in prometheus.yml, because the load's parallel senders deliver neighbouring timestamps slightly out of order:

args:
  - --web.enable-remote-write-receiver
  - --query.max-samples=1000000000   # default 50e6
  - --query.timeout=600s             # default 2m

# prometheus.yml
storage:
  tsdb:
    out_of_order_time_window: 2h

Key Mimir configuration. Ingestion limits are raised so the write path is never throttled by defaults, and the query-side ones for the same reason as Prometheus's. Mimir needs both timeouts — http_server_write_timeout also defaults to 2m and fires first:

querier:
  timeout: 600s                        # default 2m
server:
  http_server_write_timeout: 600s      # default 2m
limits:
  ingestion_rate: 20000000
  ingestion_burst_size: 20000000
  max_global_series_per_user: 150000000
  max_fetched_chunks_per_query: 20000000   # default 2e6
  out_of_order_time_window: 2h

Mimir's background timers default to hours: compaction waits up to an hour, the ingester keeps its local copy of each block for 13 hours after upload, and compacted-away blocks are kept for 12. We shortened them, so Mimir settled 26 minutes after the backfill and answers this data from object storage, the way the other systems read their disk:

blocks_storage:
  tsdb:
    head_compaction_idle_timeout: 5m       # default 1h
    retention_period: 15m                  # default 13h
  bucket_store:
    sync_interval: 1m                      # default 15m
    ignore_deletion_mark_delay: 5m         # default 1h
    ignore_deletion_mark_while_querying_delay: 4m
compactor:
  first_level_compaction_wait_period: 1m   # default 25m
  compaction_interval: 5m                  # default 1h
  cleanup_interval: 5m                     # default 15m
  deletion_delay: 10m                      # default 12h

Mimir checks two of these at startup: the while-querying delay must exceed three times sync_interval and stay below ignore_deletion_mark_delay.

VictoriaMetrics, with its per-query limits raised so the largest query is answered rather than rejected:

extraArgs:
  search.disableCache: true
  search.maxSamplesPerQuery: "2147000000"
  search.maxQueryDuration: 600s
  search.maxUniqueTimeseries: "5000000"

How the measurement is taken

Queries are issued from inside the cluster, from a pod in the same availability zone as all four systems, on a node that is not under test.

Every system's data is on node-local NVMe, so storage is not a variable between them and no query is measuring network-disk throughput.

All data is in place before anything is measured. The load finishes, every system finishes its own background work — compaction, merges, block uploads — and only then do the queries start. All four answer over the same absolutely-pinned windows, so a run repeated later sees the same bytes.

The step is computed, not pinned. A fixed 15s step makes the point count grow with the window — 1,440 points at 6h — which no dashboard would request. Grafana asks for roughly the panel width in pixels, so this benchmark uses its rule. It matters: Prometheus's and Mimir's cost grows with the number of output points, OpenObserve's with the data scanned.

How the data was generated

The load comes from openobserve/fake-webserver:v5 in backfill mode: a single job simulating 14 web-server nodes, producing 7 hours of samples at exactly 15-second spacing from a fixed seed. It sends the identical Prometheus remote-write requests to all four systems, so every system receives byte-identical data, and the same flags reproduce the same samples.

  • 2,218,011,632 samples across 1,338,330 series, the same remote-write requests to all four
  • 0 retries, 0 rejected samples on any system; each then held exactly the generated count

All four complete every window — but only because the limits were raised, on all of them. At stock settings this query does not run at all. Prometheus refuses it outright:

execution: query processing would load too many samples
into memory in query execution

Mimir refuses the wider windows:

execution: the query exceeded the maximum number of chunks
(limit: 2000000 chunks) (err-mimir-max-chunks-per-query).

VictoriaMetrics' stock search.maxSamplesPerQuery and search.maxQueryDuration stop the longer windows too, with an HTTP 422. Every one of these is a protective default doing its job; this benchmark raises them all to the same allowance, with the same 600s clock.

Over 1.18 million series and six hours, OpenObserve returns in 3.7 seconds. VictoriaMetrics takes 9.2 seconds, Mimir 27 seconds, and Prometheus more than four minutes.

The gap is widest where the most data is scanned: at 30 minutes OpenObserve is 8.2× faster than VictoriaMetrics (506ms against 4,164ms), and it holds a 2.5× lead at 6 hours.

The two filter styles behave almost identically: regex and equality matching cost essentially the same on every system — the filter type isn't the variable, scan volume is.

This is where the race is closest. On the 6-hour window OpenObserve answers in 114–134ms against VictoriaMetrics' 176–228ms — 1.5–1.7× faster — while Mimir needs about 0.65 seconds and Prometheus 4.6 seconds. On shorter windows the lead widens: at 30 minutes OpenObserve is about 4× faster than VictoriaMetrics.

Across all 16 combinations (4 queries × 4 time windows), the geometric mean latency is 120ms for OpenObserve, 374ms for VictoriaMetrics, 1,090ms for Mimir and 6,077ms for Prometheus — OpenObserve at 0.32× VictoriaMetrics' latency, 11% of Mimir's and 2% of Prometheus'.

Storage

Disk used once each system had settled, from each system's own accounting:

OpenObserve2.23 GBdata 1.55 GB + metrics index 0.67 GB
Prometheus5.43 GBblocks 1.74 GB; the last ~3 hours in head chunks 0.51 GB + WAL 3.19 GB
Mimir5.51 GBobject storage 1.94 GB; ingester WAL 2.7 GB + newest block 0.64 GB

VictoriaMetrics is the most compact, at about 0.6 bytes per sample. OpenObserve stores the same data in 2.23 GB, about one byte per sample, and that includes its metrics index — 0.67 GB, or 0.30 bytes per sample — which is what makes the queries above fast. The data itself is general-purpose columnar Parquet: the same files serve SQL as well as PromQL, and map directly onto object storage, where they typically live in production.

Prometheus keeps its most recent ~3 hours in memory-mapped head chunks and the WAL by design, so roughly two thirds of its 5.43 GB is that window. Mimir answers from the 1.94 GB compacted block in object storage; its ingester keeps the WAL and the newest block on local disk until close_idle_tsdb_timeout (13 hours) closes the idle database.

The bottom line

Put the same 2.2 billion samples and 1.34 million series in front of four systems with the same resources, and the results condense to four sentences:

  • Fastest everywhere: OpenObserve answers all 16 combinations (4 queries × 4 windows) fastest — geomean 0.32× VictoriaMetrics' latency, 11% of Mimir's and 2% of Prometheus'
  • The high-cardinality limit: the unfiltered histogram over 1.18M series and 6 hours takes OpenObserve 3.7s, VictoriaMetrics 9.2s, Mimir 26.7s and Prometheus 4m 12s — and needs raised limits on every system to run at all
  • Everyday queries: irate at 6h answers in 112ms against 339ms, 1.0s and 9.8s; filtered histograms are the closest race, 1.5–1.7× ahead of VictoriaMetrics at 6h and about 4× at 30m
  • Storage: VictoriaMetrics is the most compact at 1.32 GB; OpenObserve uses 2.23 GB including its metrics index, ahead of Prometheus at 5.4 GB and Mimir at 5.5 GB
Test notes:
  • Versions: Prometheus v3.6.0, Mimir 3.2.2, VictoriaMetrics v1.154.0, OpenObserve v1.1.1, which adds a new metrics index
  • One dedicated EC2 m7gd.4xlarge per system, local NVMe, every container 12 CPU / 24 GB with requests equal to limits, all single-node
  • Result caches disabled on every system
  • Query limits raised on all four so the million-series histogram is answered rather than refused; a 600s timeout everywhere. At stock limits Prometheus, Mimir and VictoriaMetrics refuse some of the unfiltered histogram windows
  • Data from fake-webserver v5 in backfill mode: 14 simulated nodes, 7 hours at 15s, 2,218,011,632 samples across 1,338,330 series, identical remote-write requests to all four; 0 retries, 0 rejected samples
  • Prometheus and Mimir accept the backfill with a 2-hour out-of-order window; every system finished its compaction and cleanup before the first query — VictoriaMetrics 5, Prometheus 16, OpenObserve 22 and Mimir 26 minutes after the backfill
  • Mimir's background timers shortened as shown above, so it answers this data from object storage only
  • Query windows 30m / 1h / 3h / 6h ending 2026-09-28 10:00 UTC; each cell run 5 times in two back-to-back passes, medians pooled across both
  • Filtered queries use path="/api/bar" and path=~"/api/bar"
  • Multipliers are rounded — the point is the order of magnitude, not the decimals
  • We removed Vortex from these results: with the new metrics index, OpenObserve on Vortex queries no faster than on Parquet, yet takes more than twice the disk
